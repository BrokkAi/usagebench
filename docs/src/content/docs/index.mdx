<h2 class="landing-headline">Compare usage analysis against reviewed language-server behavior</h2>

UsageBench is Bifrost's recurring conformance and regression suite for source
usages and navigation. Its cases are derived from mature language-server tests,
existing analyzer suites, and difficult real-world edges. Established language
servers provide comparison evidence and post-review calibration. The reviewed
source contract remains the authority: Bifrost should match reference-server
behavior where it satisfies that contract, and may differ when the evidence
supports another result.

Language servers are primarily designed for interactive development: completion,
diagnostics, refactoring, and cursor-local navigation inside an editor
workspace. Bifrost is designed as a code-analysis and navigation substrate for
repository-scale consumers, especially coding agents and static-analysis tool
developers. For those consumers, reliable symbol identity, source locations,
and relationships are not supporting editor features; they are the interface
through which the codebase is understood.

UsageBench tests the important overlap between those products. Parity means an
agent should not lose the navigation quality developers already expect from
their language tooling. A Bifrost-only exact result matters only when the
reviewed source contract supports it; it is not evidence that every part of an
LSP or compiler model has been surpassed.

All 158 current cases have completed a
[first human ground-truth audit](ground-truth-review/). The corpus now preserves
those decisions as executable regression contracts, and the daily workflow runs
them against Bifrost `master` so a previously satisfied semantic edge cannot
quietly disappear.

The current result starts from the synchronized UsageBench `78e66e5` run and
Bifrost `782522b2`. The Java profile and pinned Bifrost revision were rerun
after correcting JDT workspace isolation and three navigation operations.
Metals was then rerun at 1.6.8; its Scala results were unchanged. The other
eight reference profiles retain their synchronized reports. Every runner
completed without an error. The report shape remains analyzer-neutral:
language servers are the first comparison set, not a permanent limit, and
future analyzers can be added without changing the authored ground truth.

## Required destinations found

The headline metric asks the question closest to normal editor use: **did the
operation surface every reviewed destination the user needed?** A case counts
when all required references are present and every navigation or type lookup
includes its expected target. A containing range or additional result does not
turn that into a failure.

This is intentionally recall-forward. It does not say that imprecise ranges,
unrelated results, or a wrong first choice are harmless; the stricter table
below measures those differences. The denominator contains the **131 cases
scoreable by both Bifrost and the corresponding reference server**.

## Strict UsageBench contract conformance

The secondary metric requires complete reviewed token ranges, no unallowed
identity-family extras, and exactly one authored navigation target. This is a
deliberately stronger machine-consumer contract, not a generic LSP 3.18
compliance verdict. [LSP 3.18 requires a `Location` to contain a
`Range`](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.18/specification/#location),
but does not require every references or navigation range to select exactly
one terminal identifier.

Bifrost is exact on **116/131 (88.5%)** shared cases and the reference servers
on **96/131 (73.3%)**. The equal-profile means are 88.6% and 75.0%; the median
paired profile gap is +9.2 percentage points. Both sides are exact on 85 cases,
Bifrost alone on 31, the reference server alone on 11, and neither on 4.
